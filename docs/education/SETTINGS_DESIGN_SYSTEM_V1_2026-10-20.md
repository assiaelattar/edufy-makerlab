It does not change the existing Firebase destinations, role rules, account creation, import/export schema, financial repair logic, or production data. No push or deployment.

## Verification and limits

- Production `npm.cmd run build` passed after removal of the unrelated shared module stylesheet dependency. Existing Firebase static/dynamic import and large-chunk warnings remain.
- The committed baseline Design System checker passed 27 token, contrast, dialog and reduced-motion checks. The workspace's expanded, uncommitted checker was adjusted locally to recognize the Settings-owned CSS contract; it passed 62 checks after that change. The expanded checker and shared module bridge belong to other in-progress work and are not in this focused Settings commit.
- `git diff --check` passed for the focused tracked files. Repository-wide TypeScript still reports pre-existing unrelated diagnostics; a filtered Settings diagnostic run showed none.
- Browser checks showed no page-level horizontal overflow for all eight staff categories, the student and restricted branches, and empty/loading/error states at 1440px and 390px in both themes. Mobile category rail scrolls; long forms and dialogs scroll. Emulated reduced motion matched the media query and gave Settings navigation zero transition and animation duration.
- Actual signed-in Administrator navigation covered all seven accessible categories and their loaded panels on desktop and at 390 CSS pixels. Every mobile category rendered its expected panels with document width equal to viewport width; Save remained disabled. Team data loaded from zero to five accounts. No real-account screenshot was retained because it contains private school data. Real learner, restricted-role and super-admin sessions, live empty/error states, consequential dialogs and physical-phone behavior remain outside this check.
- Opening Integrations in a fresh signed-in tab initially marked Settings dirty without an edit, apparently from an unfocused browser autofill/change event on a key field. The key handlers now accept changes only while their input has focus. Repeating the read-only open after that fix left Save disabled; a focused synthetic edit still enabled Save. No key value was exposed or written.
- Isolated file input tests used the in-app browser file chooser with local fixture paths; no Chrome extension permission change was needed. Valid academy and document logos produced 1×1 WebP previews and enabled Save. Invalid images kept Save disabled and showed a readable inline error. Opening a picker without selecting a file left the form clean. Valid CSV imported one mocked row; missing phone skipped one; mixed data reported one accepted and one skipped; a mocked Firestore rejection reported one failure; empty and header-only files showed specific errors. CSV inputs reset after each result so the same file can be retried. No production upload or write occurred.
- Physical-phone behavior remains unverified.

**Acceptance gate:** the Administrator-accessible read-only category tour is complete. Settings remains an implementation candidate until the real learner, restricted-role and super-admin branches, physical-phone behavior and any required real write acceptance are explicitly reviewed. Preserve the synthetic/real-account distinction when integrating or releasing.
